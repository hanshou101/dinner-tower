### Spawning the server in a test: TypeScript rejects `stdio: ["ignore", "pipe", "pipe"]` when annotated as `ChildProcessWithoutNullStreams`

- Tool / API / SDK: TypeScript 5.9 + `@types/node` 20.19, Node 20.19.4
- Task attempted: spawn `tsx src/index.ts` from a vitest test and keep typed handles on `stdout` / `stderr`.
- Steps taken: declared `const child: ChildProcessWithoutNullStreams = spawn(cmd, args, { stdio: ["ignore", "pipe", "pipe"] })`, then `npx tsc --noEmit`.
- Expected: the child is a `ChildProcess` with readable stdout/stderr, so the type fits.
- Actual: `test/helpers.ts(48,9): error TS2322: Type 'ChildProcessByStdio<null, Readable, Readable>' is not assignable to type 'ChildProcessWithoutNullStreams'. Types of property 'stdin' are incompatible. Type 'null' is not assignable to type 'Writable'.`
- Severity: Minor
- Workaround: dropped the explicit annotation and let TypeScript infer `ChildProcessByStdio<null, Readable, Readable>` (or annotate exactly that type).
- Actionable suggestion: Node's typings have no "readable-only child" alias; use `ChildProcessByStdio<null, Readable, Readable>` (or inference) whenever stdin is `"ignore"`.

### MCP SDK v2 split packages ship no per-symbol API docs; the signature lives in one generated `.d.mts` bundle

- Tool / API / SDK: `@modelcontextprotocol/server@2.3.1`, `@modelcontextprotocol/node@2.1.1`, `@modelcontextprotocol/express@2.0.2`
- Task attempted: find how to construct an `McpServer` with `instructions`, how to register a tool with an input schema and annotations, and which transport options make Streamable HTTP stateful.
- Steps taken: read `node_modules/@modelcontextprotocol/server/README.md` (1.9 KB, points at the external site `ts.sdk.modelcontextprotocol.io/v2/`; nothing version-pinned in the package, and there is no `docs/` folder) — only `dist/index.mjs` plus a 4000-line `dist/index.d.mts`. Grepped `declare class McpServer`, `McpServerOptions`, `WebStandardStreamableHTTPServerTransportOptions` in that file. The first lines are a re-export of minified aliases (`w as McpServer`, `T as McpServerOptions`), so `grep McpServer` first lands on an import list, not the class.
- Expected: a per-export declaration file or a doc page matching the installed version (every v1 tutorial online is for `@modelcontextprotocol/sdk` and does not apply).
- Actual: no error, just time lost. Two extra traps: `registerTool` has two overloads and the raw-shape one is marked `@deprecated` (must pass `z.object({...})`), and `isInitializeRequest` is exported from `@modelcontextprotocol/server`, not from the `/types`-style subpath a v1 user would look for.
- Severity: Minor
- Workaround: treat `dist/*.d.mts` as the source of truth — `grep -n "declare class McpServer" -A 80`, `grep -n "interface WebStandardStreamableHTTPServerTransportOptions" -A 60`; confirm exports at runtime with `node --input-type=module -e "import * as m from '@modelcontextprotocol/server'; console.log(Object.keys(m))"`.
- Actionable suggestion: the SDK could ship one `API.md` per split package generated from the declarations, and list the v2 constructor/registerTool signature on the package README.
