# T7 friction log

### Quick start never builds the simulator, so the page a judge opens is a 503

- Tool / API / SDK: `scripts/dev.sh` (bash) + `sim/server.ts` (Express 5) + root `README.md` Quick start, at commit `18b2a45`
- Task attempted: follow the root README from a brand-new clone — `npm --prefix server install` / `sim` / `board` / `scheduler`, `cp .env.example .env`, `bash scripts/dev.sh`, then open <http://localhost:8080>.
- Steps taken: cloned into an empty directory, ran exactly those six steps; `dev.sh` printed `Building the board…`, started the MCP server, warned `[sim] …/sim/dist/index.html is missing — run: npm --prefix sim run build`, then still printed `Dinner Tower is up`. `curl -s -o /dev/null -w '%{http_code}' http://localhost:8080/` returned `503`.
- Expected: the README's last step produces a page that opens; `dist/` is gitignored, so anything the page needs must be built by `dev.sh` or by a step the README lists.
- Actual: `HTTP 503`, body `Simulator is not built. Run: npm --prefix sim run build`. `dev.sh` builds `board/` but not `sim/`, and the README's Quick start never asks for `npm --prefix sim run build` (only `sim/README.md` does). A judge following the root README sees a plain-text error page — no board, no conversation, no product.
- Severity: Blocker (for anyone following the README; AC-8 and AC-9 are unreachable that way)
- Workaround: `npm --prefix sim run build` before `bash scripts/dev.sh`; the page then answers `200` with 4627 bytes.
- Actionable suggestion: add `npm --prefix sim run build` to `scripts/dev.sh` right after the board build (the board is already built there for the same reason), and mirror it in the root README Quick start. Capture: `proof/T7-README-quickstart.txt`.

### The one-key starter says "up" while the page is down

- Tool / API / SDK: `scripts/dev.sh` readiness loops (curl against `/health` and `/api/config`)
- Task attempted: trust `dev.sh`'s "Dinner Tower is up" line as the signal that the app is usable.
- Steps taken: started `dev.sh` on a clone where `sim/dist` did not exist; it polled `http://127.0.0.1:8080/api/config` (200 even with no page), printed the success banner, and stayed running.
- Expected: a line that says the stack is up means the thing a user opens (/) works.
- Actual: `/api/config` is served by the same Express app that answers `/` with 503, so the readiness probe cannot distinguish "server process alive" from "page usable". The banner printed, the page 503'd.
- Severity: Major
- Workaround: probe `GET /` (or `/index.html`) in the readiness loop.
- Actionable suggestion: readiness checks should hit the same URL the README tells the user to open, not a config endpoint.

### Board rows during the 5 s "changed" highlight do not photograph reliably

- Tool / API / SDK: Playwright 1.64.1 (chromium headless, `page.screenshot`), board MCP App (`board/src/board.css` `@keyframes row-flash`, `CHANGE_HIGHLIGHT_MS = 5000`)
- Task attempted: capture a screenshot right after `report_delay` to show the moved rows, as AC-8 evidence.
- Steps taken: clicked `+10 MIN` on the board, waited 2.5 s, full-page `page.screenshot({ animations: "disabled" })`; the image showed the TIME column's first digit clipped on the changed rows (`6:37` rendered like `3:37`, `6:40` like `5:40`). Measured the row and its time cell with `getBoundingClientRect` during and after the highlight: identical (`row x=14 w=832`, `cell x=14 w=84`, `textContent "6:37 PM"`), and a screenshot 6 s later is clean.
- Expected: a screenshot taken 2.5 s into a 5 s highlight shows the same text the DOM holds.
- Actual: the glyphs are clipped only while the row-flash animation is running; DOM text and layout are unaffected. Two re-captures were needed before the evidence was readable. The same effect would hit a screen recording of the demo if the flashing rows are meant to be read out.
- Severity: Minor
- Workaround: take screenshots after the 5 s highlight expires (and/or open the page with `prefers-reduced-motion: reduce`), which is what `proof/T7-AC8-03-board-after-plus10.png` does.
- Actionable suggestion: either accept it (the flash is decorative) or drop the `background` animation on `.row.changed` and keep only the static amber left bar, so text rasterisation stays identical.

### Running the repo's own verifier rewrites ten committed screenshots

- Tool / API / SDK: `bash scripts/verify.sh` (Playwright E2E inside `sim/`, `board/`)
- Task attempted: run the verifier twice on a clean checkout, then commit only the files this ticket owns.
- Steps taken: `git status --short` before the run was clean; after two `bash scripts/verify.sh` runs it listed `M proof/T3-0*.png` (6), `M proof/T5-e2e-real.png`, `M proof/T6-agent-0*.png` (3) — ten tracked images — even though nothing under test changed.
- Expected: a verifier reports pass/fail without modifying tracked files.
- Actual: the E2E specs write their screenshots straight into `proof/` (`sim/test/e2e/sim.spec.ts`, `board/test/real/board-real.spec.ts`), so every local run leaves the working tree dirty and makes "commit only my files" error-prone.
- Severity: Minor
- Workaround: `git checkout -- proof/T3-*.png proof/T5-*.png proof/T6-*.png` before committing; the ticket only stages `proof/T7-*`.
- Actionable suggestion: have the E2E specs write to `test-results/` (already gitignored) and copy into `proof/` only from a dedicated script, or add a `--update-proof` flag.
