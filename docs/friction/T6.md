# T6 friction log

### No OpenAI-compatible endpoint anywhere on this machine

- Tool / API / SDK: OpenAI-compatible `chat/completions` (any provider)
- Task attempted: the ticket's first 10-minute check — can this machine run a tool-calling chat completion against an existing DeepSeek / GLM / Qwen account or relay.
- Steps taken: checked the environment and local configuration for an OpenAI-compatible endpoint with a key a product may use; checked for a local model server on 11434 / 1234 / 8000 / 4000 / 3000 and for `ollama` / `llama-server` / `lmstudio`.
- Expected: at least one endpoint answers `/models` with 200.
- Actual: no endpoint with a product-usable key was available on the build machine, and no local model server was running.
- Severity: Blocker (AC-10 only — everything else in the ticket was built and tested)
- Workaround: implemented the whole agent path against a scripted OpenAI-compatible endpoint in the E2E test, and marked AC-10 `need_local`; the page disables agent mode with the SPEC §6.5 hint when the keys are absent.
- Actionable suggestion: for hackathon projects that need a model, provision one workspace-level OpenAI-compatible key (with a spend cap) before opening the LLM-dependent tickets, instead of discovering the gap inside the time box.

### The ticket's test path is not discovered by either test runner

- Tool / API / SDK: vitest 4.1.12 (`sim/vitest.config.ts`: `include: ["test/unit/**/*.test.ts"]`), @playwright/test 1.64.1 (`sim/playwright.config.ts`: `testDir: "./test/e2e"`)
- Task attempted: put the agent tests at the path the ticket names, `sim/test/agent*.test.ts`, and have `npm --prefix sim test` run them.
- Steps taken: checked both configs; a file directly under `sim/test/` matches neither `test/unit/**` nor `test/e2e/**`.
- Expected: the ticket's path and the runners' discovery rules agree.
- Actual: nothing under `sim/test/*.test.ts` would ever run — `npm --prefix sim test` would stay green while the new tests silently never executed.
- Severity: Minor
- Workaround: `sim/test/unit/agent.test.ts` (vitest) and `sim/test/e2e/agent.test.ts` (Playwright), same `agent*.test.ts` basename; the two config files were outside this ticket's allowed paths, so they were left untouched.
- Actionable suggestion: write ticket paths as globs that match the runners' config, e.g. `sim/test/{unit,e2e}/agent*.test.ts`.

### `bash scripts/dev.sh &` ignores SIGINT, so a scripted Ctrl-C test left orphans

- Tool / API / SDK: bash 3.2 (macOS), `trap cleanup INT TERM EXIT`
- Task attempted: start `scripts/dev.sh` from a non-interactive harness, then send SIGINT to verify that both servers stop.
- Steps taken: `bash scripts/dev.sh > log 2>&1 &`, `kill -INT $!`, then `lsof` the three ports.
- Expected: the trap runs and both children exit.
- Actual: the ports stayed open — POSIX shells start background jobs with SIGINT ignored when job control is off, so the trap never fired. `kill -TERM $!` did run the trap and both children exited (`[dinner-tower] SIGTERM — closing 0 session(s)` / `Stopped.`).
- Severity: Minor
- Workaround: cleanup is verified with SIGTERM in automation; in a real terminal Ctrl-C signals the whole foreground process group, so the interactive path stops both processes.
- Actionable suggestion: keep one-key dev scripts in the foreground (`exec` the long-running child) or have the cleanup also trap `SIGHUP` and watch the parent, so PID-based shutdown does not depend on which signal the harness sends.

### An `.env` copied from `.env.example` exports empty strings that defeat `?? "default"`

- Tool / API / SDK: bash 3.2 `set -a; . ./.env`; Node 20 `process.env`; `server/src/clock.ts`
- Task attempted: the README Quick start — `cp .env.example .env`, fill only the three `LLM_*` keys, `bash scripts/dev.sh`.
- Steps taken: copied the example (every key present, most empty), started the dev script. Found in review on the second Mac mini; reproduced here with a temp copy via `ENV_FILE`.
- Expected: empty values mean "not set", so the server falls back to its documented defaults.
- Actual: `set -a` exports `DEMO_CLOCK_START=""`, and `process.env.DEMO_CLOCK_START ?? "13:00"` does not apply to an empty string → `Error: DEMO_CLOCK_START must be "HH:MM", got ""` at `createClock`, server exits, dev script stops.
- Severity: Major (blocks the documented first-run path)
- Workaround: `dev.sh` now unsets every key whose value is empty after sourcing the file, so `??` and `:-` defaults apply as written.
- Actionable suggestion: when a repo ships `.env.example` with blank values, any launcher should treat `KEY=` as unset (or `.env.example` should carry the real defaults and the loader should not special-case them). The two conventions are easy to mix and the failure only shows up on a fresh clone.
