# T4：規劃工具 — friction log

本票親手踩到的坑（格式照 `docs/friction/README.md`），後面附一節「親手驗證過的協議行為」，那是驗證記錄，不是坑。

## Friction

### TypeScript `NodeNext` vs `Bundler`: importing the scheduler from the server

- Tool / API / SDK: TypeScript 5.9 · `server/tsconfig.json` (`moduleResolution: "NodeNext"`) · `scheduler/tsconfig.json` (`moduleResolution: "Bundler"`)
- Task attempted: SPEC §6.1 says the `server` package imports the engine directly (`import … from "../../../scheduler/src/index.ts"`). Add the first such import in `server/src/plan/view.ts`.
- Steps taken: wrote `import { schedule } from "../../../scheduler/src/index.js"`, then `npx tsc --noEmit` in `server/`.
- Expected: type-check passes — both packages are `"type": "module"` ESM and `tsx` runs either one.
- Actual: nine errors, one per extensionless relative import inside the engine:
  ```
  ../scheduler/src/index.ts(7,15): error TS2835: Relative import paths need explicit file extensions in ECMAScript imports when '--moduleResolution' is 'node16' or 'nodenext'. Did you mean './types.js'?
  ```
- Severity: Major
- Workaround: appended `.js` to the 18 relative imports under `scheduler/src/` (no behaviour change; `npm --prefix scheduler test` still 39 passed and its own `tsc --noEmit` still clean).
- Actionable suggestion: when one package is consumed by another in a repo with per-package `tsconfig.json`, settle on one `moduleResolution` (or publish the engine as a built package). A repo-level note in the SPEC would have saved a round trip — the error only appears at the moment of the first cross-package import, which is exactly when a ticket author is least expecting compiler noise from another ticket's directory.

### `elicitInput` is deprecated in the SDK typings, but the modern replacement does not exist on 2025-11-25

- Tool / API / SDK: `@modelcontextprotocol/server` 2.3.1
- Task attempted: call form elicitation from inside a `tools/call` handler, on a server that negotiates protocol **2025-11-25**.
- Steps taken: read `Server.elicitInput` in the typings; the JSDoc says "Deprecated. Throws on a 2026-07-28-era request — use `inputRequired` (multi-round-trip) instead", and `Server._assertPushApiInServedEra` backs that up.
- Expected: a single obvious API to call.
- Actual: two eras, two idioms — push-style `elicitInput` on 2025-era sessions, `input_required` results on 2026-07-28. The `inputRequired(...)` path the JSDoc steers to is not available on the 2025-11-25 wire the competition asks for, so the deprecation notice is misleading for anyone pinned to the 2025 revision.
- Severity: Minor
- Workaround: kept `server.server.elicitInput({ mode: "form", … })` (the 2025-era path) and asserted the negotiated version (`2025-11-25`) in the T2 tests, which proves the era.
- Actionable suggestion: make the JSDoc conditional on the negotiated era, or mark the method "era-specific" rather than "deprecated" when the server serves 2025.

### An empty `elicitation: {}` capability is rewritten to `{form:{}}` before the server sees it

- Tool / API / SDK: `@modelcontextprotocol/core` 2.3.1 · `ClientCapabilitiesSchema`
- Task attempted: gate the oven question on "client supports form elicitation", and unit-test the four shapes a client can advertise (`undefined`, `{}`, `{form:{}}`, `{url:{}}`).
- Steps taken: parsed each shape through `ClientCapabilitiesSchema` and printed `capabilities.elicitation`.
- Expected: `{}` stays `{}`.
- Actual: `{"elicitation":{}}` → `{"form":{}}`. The transform is helpful in production but means a raw `{}` never reaches the server through a real handshake, so the "`{}` means form support" rule can only be exercised as a pure unit test.
- Severity: Minor
- Workaround: `supportsFormElicitation()` is a pure function over the raw shape (unit-tested with all four), and the integration test uses a real client that declares `{form:{}}`.
- Actionable suggestion: document the normalisation next to the capability schema.

## 親手驗證過的協議行為（不是坑）

- **有狀態會話**：`initialize` 發 `Mcp-Session-Id`，同一會話的後續 `tools/call` 都帶這個 id 並落在同一個 `McpServer` 實例上。伺服器在 `tools/call` 的 SSE 串流裡發出 `elicitation/create`，客戶端的處理器回覆後，同一次 `tools/call` 繼續跑完並回 PlanView——`test/plan.test.ts` 三個 elicitation 測項就是這樣跑的（accept share-oven / accept keep-temps / decline），每次都收到恰好一次請求。
- **無狀態（每請求新建 server）會壞在哪**：如果照官方範例的無狀態寫法，`tools/call` 與 elicitation 的回覆會落在不同實例上，`elicitInput` 的 promise 沒有人 resolve。T2 已經按 SPEC 做成有狀態（`sessionIdGenerator: () => randomUUID()`、按 session id 存 transport），本票直接受益；`plan.test.ts` 的 plain 客戶端與 eliciting 客戶端是同一個伺服器進程的兩個會話，能力判定各自獨立（plain 客戶端從沒收到 elicitation 請求，回的是 `conflict.options`）。
- **`oneOf` titled enum 被 SDK 接受**：SPEC §6.3 的 `requestedSchema` 用 `oneOf: [{const:"share-oven",title:…},{const:"keep-temps",title:…}]`，`@modelcontextprotocol/core` 2.3.1 的 `ElicitRequestFormParamsSchema` 原樣接受並原樣送到客戶端（`oneOf` 沒有被剝掉，兩個 `const` 都在），因此**沒有**動用 SPEC 的 `enum`+`enumNames` 備案。驗證方式：`ElicitRequestFormParamsSchema.parse()` 的 round-trip，加上真實客戶端收到的 `requestedSchema.properties.choice.oneOf` 恰為兩個 id。
