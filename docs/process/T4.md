## 6. 偏差與建議

- **跨包 import 的副檔名**：SPEC §6.1 要求 `server` 直接 import `../scheduler/src/index.ts`，但 `server/tsconfig.json` 是 `moduleResolution: NodeNext`，而 `scheduler` 的相對 import 沒有副檔名（它自己的 tsconfig 是 `Bundler`）。第一次 `npx tsc --noEmit` 直接 9 條 TS2835。已在 `scheduler/src/` 補 `.js`（行為不變、scheduler 39 個測試與 typecheck 仍綠）。**建議**：把「跨包 import 的 tsconfig 相容性」寫進 SPEC §6.1，或統一各包 `moduleResolution`。
- **`whats_next` 會帶 conflict**：當存的計劃是 keep-temps 且有等待違規時，`whats_next` 會把 §6.2.3 的 conflict（message / 兩個選項 / waits）一起回，看板才有頂部橫幅可以切換方案（T5 的 AC-8 只用 share-oven，不受影響）。SPEC §6.3 沒明說 `whats_next` 的 `conflict` 該回什麼，這裡選了「如實回」。
- **`option` 在無衝突時被忽略**：沒有衝突時 `plan_dinner` 一律回 `option:"primary"`，即使呼叫方傳了 `option`。SPEC 只定義了有衝突時兩個選項的語義。
- **只提供 keep-temps 時不反問**：`shareOven === null` 時直接回 primary + `conflict`，符合 §6.2.3 最後一條；即使客戶端支持 elicitation 也不發請求（測項「不聲明 elicitation 的客戶端」與此無關，是能力判定那條在管）。
- **測試夾具**：`server/test/fixtures/board.html` 是給 `DT_BOARD_HTML` 的測試夾具，真看板由 T5 建到 `board/dist/board.html`；本票沒有建 `board/` 任何檔案。
- **建議（不屬於本票）**：`plan_dinner` 的 `dishes` 上限 8 寫在 zod（超過是協議層 invalid params，不是工具結果 `isError`），與 `update_kitchen` 的處理方式不同；若要一致，可把上限校驗挪進 handler。T6 的代理模式把 `tools` 轉 OpenAI function 時，`plan_dinner` 的 `dishes` 陣列與 `serveAt` 字串都能直接映射，不需要額外處理。
